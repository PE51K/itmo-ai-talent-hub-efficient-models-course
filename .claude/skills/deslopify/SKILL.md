# Deslopify

The rules are in `AGENTS.md` at the repository root: writing rules 5-46 for prose, code rules 47-57 for code. Read it first; this skill defines the procedure, not the rules.

## Scope

1. With a path argument, check the files under that path.
2. With `all`, check every tracked file: `git ls-files`.
3. With no argument, check the files in `git diff --name-only HEAD` plus untracked files from `git status --short`.

Skip `Efficient-Models-course-ITMO-2026/` (a submodule with course materials), `uv.lock`, binary files, generated results (`results/**/*.json`, `*.csv`, `*.png`, `*.pt`), and notebook outputs. In a `.ipynb` file, check markdown cells and code cell sources.

## What to check

For prose (`.md`, `.tex`, notebook markdown, docstrings, comments, the last commit message if the scope is the diff), go through rules 5-46 in order. Start with the ones that need reading, not grepping: sentences without a checkable statement (5), numbers without units, seeds, or hardware (6), causes without a controlled comparison (8), unmeasured times not labeled as estimates (10), headings over results that do not state the result (13), synonym rotation for one concept (17), text about the text (29-30).

For code (`.py`, notebook code cells), go through rules 47-57: self-evident comments, emojis, long-winded expressions and docstrings, unnecessary checks, duplicated logic, deep nesting, then error handling, structure, naming, completeness, and results backed by files.

A grep pass finds the lexical patterns fast; it does not replace reading. Useful starting points:

```sh
git grep -n -i -E "delve|crucial|pivotal|seamless|comprehensive|holistic|leverage|utiliz|showcase|underscore|tapestry|testament|notably|in summary|in conclusion|it is worth noting|it is important to note|not only|not just" -- ':!Efficient-Models-course-ITMO-2026'
git grep -n -P "\x{2014}|[\x{201C}\x{201D}\x{2018}\x{2019}]" -- ':!Efficient-Models-course-ITMO-2026'
git grep -n -P "[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]" -- ':!Efficient-Models-course-ITMO-2026'
git grep -n -E "# (Step [0-9]|=====|-----)" -- '*.py'
git grep -n -E "except Exception|except:" -- '*.py'
```

## How to fix

1. Fix each violation in place. Rewrite the sentence around its specific fact or delete it; deleting the flagged phrase alone usually leaves an empty sentence.
2. Do not change meaning, numbers, results, or behavior. In code, a fix is behavior-preserving: removing a comment, flattening nesting, merging duplicated blocks into a loop, deleting a check that cannot fire. When a fix would change behavior (an always-false check that hides a bug, an ignored exception), do not apply it; list it for the user.
3. Do not add content to make a sentence specific when the fact is not in the repository. Flag it for the user instead ("README.md:40, the speed-up has no hardware").
4. Keep the diff to the violations; do not reformat or restyle untouched lines.
5. For code, run what exists after the edits: `uv run python <script> --help` or the project's smoke mode (`uv run python kd.py --smoke` in `project/`), so that a fix did not break an import or a name.

## Report

Reply to the user in their language, short: how many files changed, then the items that need a decision, each as `path:line` with the rule number and one line on what is missing or what the behavior change would be. Do not list the fixes that were applied; they are in the diff.
